Regex Debugging

JavaScript Regex Flags and Stateful test()

Runnable examples checked October 15, 2026.

If the same input passes validation once and fails on the next call, inspect the flags before changing the pattern. This guide separates repeated validation from text scanning and shows the expected result of each example. Use synthetic inputs so debugging does not expose customer addresses or production logs.

Recommended workflow

StepWhy it matters
Start without flagsProve the core pattern before changing matching semantics.
Add one behaviorEnable case, multiline, dot-all or Unicode handling independently.
Test stateful APIsGlobal and sticky JavaScript regex objects update lastIndex across calls.
Verify engine supportFlag names and behavior differ across JavaScript, Python, Java, PHP and command tools.

Reproduce alternating validation results

const identifier = /^dev$/g;
console.log(identifier.test("dev"), identifier.lastIndex); // true 3
console.log(identifier.test("dev"), identifier.lastIndex); // false 0
console.log(identifier.test("dev"), identifier.lastIndex); // true 3

Global and sticky expressions retain a cursor in lastIndex. A successful call moves that cursor; a failed call resets it. In this anchored example, the second call starts after the first match and fails. This behavior is documented in MDN's lastIndex reference.

Choose validation or scanning deliberately

// Independent yes/no validation: no global or sticky state.
const identifier = /^dev$/;
console.log(["dev", "dev", "other"].map(value => identifier.test(value)));
// [true, true, false]

// If an existing scanner must be reused, reset before each independent input.
const scanner = /dev/g;
for (const value of ["dev", "dev"]) {
  scanner.lastIndex = 0;
  console.log(scanner.test(value)); // true, then true
}

Do not reset the cursor inside an iteration intended to collect successive matches; that would keep returning to the same position. For a form field, the stateless pattern is simpler. For extraction, use a scanner and keep its lifecycle tied to one input. The email validator explains why its multiline sample uses different flags from a single-field form check.

Flag comparison matrix

ExpressionInputResultInterpretation
/^dev$/dev\nopsfalseThe whole input is not dev.
/^dev$/mdev\nopstrueA line matches.
/dev.ops/dev\nopsfalseDot excludes the newline.
/dev.ops/sdev\nopstrueDot includes the newline.

Here \n denotes an actual newline in the input. A practical failure case is a form validator using m: a valid first line can hide unwanted extra lines. Test the entire field and decide explicitly whether newlines are acceptable. Changing m does not change what dot matches.

Sticky matching is not a search ahead

const token = /dev/y;
token.lastIndex = 0;
console.log(token.test(" dev")); // false
token.lastIndex = 1;
console.log(token.test(" dev")); // true

Sticky matching requires the token at the cursor position. It is useful when a tokenizer must reject a gap instead of skipping ahead. Reproduce these JavaScript examples in your runtime; the Formalint Regex Matcher exposes g, i, m, s and u, but does not currently offer a sticky cursor control.

Review checks

  • Test anchors with multiple lines.
  • Include non-ASCII case examples.
  • Reset lastIndex in reused JavaScript patterns.
  • Record flags beside stored patterns.

Common mistakes

  • Using multiline to make dot match newlines.
  • Reusing a global regex in repeated validation calls.
  • Assuming case-insensitive Unicode behavior is identical everywhere.

Record the input, expression, flags, previous calls and lastIndex when reporting a regex bug. A pattern alone may not reproduce a stateful failure.
